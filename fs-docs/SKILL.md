# 文档编写规范 (fs-docs)

## README 标准结构(项目根目录, 新访客 5 分钟可跑起来)

```markdown
# 项目名
一句话简介 + 徽章(构建/测试/许可证)

## ✨ 功能特性(3-6 条要点)
## 🖥️ 演示(截图/GIF/线上地址)
## 🛠 技术栈(列表 + 版本)
## 🚀 快速开始
   1. 环境要求(Node 版本、包管理器)
   2. 使用项目声明的包管理器安装依赖
   3. 配置 .env(见下表)
   4. 运行项目声明的开发脚本
## 📁 目录结构(带注释的树)
## ⚙️ 环境变量(表格: 变量名/说明/是否必填/示例)
## 📜 可用脚本(表格: 命令/作用)
## 🗄 数据库(迁移/种子命令)
## 🚢 部署(平台说明 + 步骤)
## 📄 许可证
```

- 快速开始必须**实际验证过**(复制粘贴能跑通)
- 项目结构变化、新增环境变量、新脚本, 立即同步 README(与代码同 PR)

## API 文档

- 以 OpenAPI 3.1 为准自动生成(见 fs-backend), 手工维护会漂移
- 每个接口文档含: 用途、鉴权要求、请求参数、响应示例、错误码表

## 架构与决策

- 架构图/说明放 `docs/architecture.md`(随阶段 0/4 更新)
- **重要决策写 ADR**(`docs/adr/NNNN-标题.md`): 背景 → 决策 → 备选 → 后果; 决策被推翻时新增 ADR 而不是改写历史
- 需要 ADR 的场合: 技术选型、数据库方案、架构模式、重大取舍

## CHANGELOG(Keep a Changelog 格式)

- 按版本记录: Added / Changed / Fixed / Removed
- 语义化版本: 破坏性变更升大版本, 新功能升小版本, 修复升补丁
- 发布时更新, 不靠 commit log 代替

## 代码注释原则

- 写"为什么"(业务规则、坑、权衡), 不写"是什么"(重复代码本身)
- 公共 API/导出函数写 JSDoc(参数、返回、异常、示例)
- 复杂算法/正则配注释或拆小函数; TODO 注释必须带负责人/issue 号
- 禁止注释掉的死代码(用 Git 历史找回)

## 完成门禁

- [ ] README 按标准结构齐全, 快速开始实测通过
- [ ] API 文档自动生成且与代码一致
- [ ] 关键决策有 ADR 记录
- [ ] CHANGELOG 更新到当前版本
- [ ] 全项目注释符合原则(无死代码、无废话注释)
