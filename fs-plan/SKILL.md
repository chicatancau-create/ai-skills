# 需求分析与技术选型 (fs-plan)

## 执行流程

### 1. 需求澄清(先问, 再动手)

优先从仓库与用户请求推断以下信息；仅当缺失信息会实质改变方案时，集中提出少量问题：

- **目标用户与场景**: 谁用? 解决什么问题?
- **核心功能**: 最重要的 3 个功能(MVP 范围)
- **规模预期**: 用户量级、数据量级(决定架构复杂度的关键)
- **形态与端**: Web / 移动端 / 桌面? 是否需要登录?
- **部署环境**: 云平台托管(Vercel 等)/ 自有服务器 / 个人学习项目?
- **团队情况**: 单人开发还是团队协作?

### 2. 技术选型决策

默认采用 `fs-fullstack` 的默认栈, 除非需求明确要求其他。选型原则:

1. **简单优先(Monolith First)**: 初期一体化部署, 不拆分微服务, 除非规模预期明确需要
2. **生态成熟度 > 新颖度**: 选社区活跃、文档完善、LTS 版本
3. **数据层按约束选择**: 优先选择项目已有数据层和迁移工具；新项目根据一致性、查询模型、运维条件和官方支持资料选择，不把某一数据库永久写死
4. **记录决策理由**: 每项选型写一句"为什么", 供后续回看

### 3. 最新标准核对(必须执行)

新建项目或升级依赖且需要写版本号时，使用当前智能体可用的官方文档工具核对以下来源；已有项目优先遵循锁文件和兼容约束：

- 运行时与框架官方文档、发布支持表和迁移指南
- 依赖仓库的锁文件、引擎兼容矩阵和当前安全公告
- 数据库/云平台官方版本支持页与升级说明

将“核对日期、来源、选定版本或范围、兼容性结论”写进技术栈决策；不要复制一份会过期的固定版本表。

### 4. 产出物(写入 `docs/` 目录)

1. **`docs/requirements.md`** 需求文档:
   - 项目概述(一句话 + 一段话)
   - 目标用户与场景
   - 功能清单(MVP 标记 ★, 后续迭代标记)
   - 非功能需求(性能/安全/兼容性)
   - 明确不做的事(Out of Scope, 防止范围蔓延)
2. **`docs/tech-stack.md`** 技术栈决策:
   - 每层选型 + 核对来源/日期 + 版本范围或锁定版本 + 一句话理由
   - 备选方案及弃用理由
3. **`docs/architecture.md`** 架构草案:
   - 系统框图(文字描述即可): 前端 ↔ API ↔ 数据库 ↔ 外部服务
   - 核心数据模型草案(实体 + 关系, 详细设计留给 `fs-database`)
   - 模块划分与目录结构草案
4. **`docs/milestones.md`** 里程碑计划:
   - 按 fs-fullstack 的 9 阶段拆分, 每个里程碑有明确的完成标准

### 5. 完成门禁

- [ ] 三份文档齐全且经用户确认
- [ ] 所有需要落地的版本号或范围来自本次官方核对, 不是凭记忆
- [ ] MVP 范围明确, Out of Scope 已写清
- [ ] 记录阶段结果；无关键阻塞时继续进入阶段 1(fs-scaffold)
