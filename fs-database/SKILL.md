# 数据库设计与数据层 (fs-database)

## 建模流程

1. 从 `docs/architecture.md` 的数据模型草案出发, 列出实体
2. 明确关系(1:1 / 1:N / N:M)与级联行为(删除时是级联/置空/限制)
3. 每个实体列出字段: 名称、类型、约束(非空/唯一/默认值)
4. 识别查询模式(按什么字段查? 排序? 关联?), 据此设计索引

## 命名与类型规范

- 表名复数 `snake_case`(如 `users`、`order_items`); 列名 `snake_case`; 关联列 `user_id`
- 主键: 根据数据库能力、分布式需求和对外暴露风险选择 UUID/ULID/自增等策略，并在架构文档说明理由
- 时间列: `created_at` `updated_at`(`timestamptz` 必带时区); 删除优先软删除(`deleted_at`)
- 布尔: `is_active` 风格; 枚举: 数据库 enum 或字符串 + CHECK 约束, 避免纯魔法字符串
- 字符串长度: 明确 `varchar(n)` 或 `text` + 应用层校验; 金额 `numeric(12,2)` 或最小单位整数
- 外键: 必须定义 `ON DELETE` 行为, 不写默认 RESTRICT 可能导致误删失败

## 索引规范

- 为高频查询的 WHERE/JOIN/ORDER BY 字段建索引, 复合索引按最左前缀设计
- 唯一性用唯一索引(防竞态, 不只是应用层校验)
- 避免: 在低基数字段(如 gender)上盲目建索引; 在长 text 上建 btree(用 GIN/tsvector)
- 迁移后跑慢查询检查, 用 `EXPLAIN ANALYZE` 验证索引命中

## 迁移纪律

- 迁移文件由工具生成(Prisma migrate), 人工不手改已应用的迁移
- 迁移必须**可回滚**(有 down 或备份策略), 上线前先在 staging 演练
- 大表变更: 加列可在线(带默认值), 删列/改类型先兼容双写再切换
- 迁移与代码同 PR 提交, 保证版本一致

## ORM/查询工具使用规范

- 选定 ORM/查询工具的 schema 或迁移文件作为唯一数据源, 不手工修改已应用迁移
- 查询时明确 select 需要的字段, 避免全表字段拖回
- 关联查询用 `include`, 注意**嵌套层级控制**(避免深嵌套爆炸)
- **防 N+1**: 用 `include`/`findMany` 批量取关联数据; 循环里查库 = 红灯
- 事务: 多步写入必须 `prisma.$transaction`(交互式事务用于条件判断)
- 并发: 更新用 `updateMany` 带条件或乐观锁(`version` 字段), 关键操作防丢失更新

## 数据安全

- 密码哈希、token 等敏感字段只存摘要, 不存明文
- 备份策略明确(每日全量 + WAL), 写进 `docs/` 并在部署阶段落实
- 生产环境连接串放密钥管理, 不给应用最高权限账号(最小权限原则)

## 完成门禁

- [ ] ER 关系与级联行为明确并记录在 `docs/architecture.md`
- [ ] 索引设计经查询模式推演, 高频查询有 `EXPLAIN` 佐证
- [ ] 迁移可回滚, 与代码同步提交
- [ ] 无 N+1(循环查询全部改为批量)
- [ ] 事务边界明确, 关键写操作有并发保护
- [ ] 输出阶段报告, 等确认后进入阶段 5(fs-testing)
