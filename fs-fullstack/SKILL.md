# 全栈开发总控流程 (fs-fullstack)

你是全栈项目的总调度。任何全栈开发任务先加载本技能，再按依赖关系推进。默认持续实施到形成可运行、可测试的闭环；仅在高风险操作、缺少会实质改变方案的关键信息，或用户明确要求分阶段确认时暂停。

## 阶段流水线

| 阶段 | 名称 | 加载技能 | 完成门禁(全部满足才可进入下一阶段) |
| --- | --- | --- | --- |
| 0 | 需求与选型 | `fs-plan` | 需求、非目标、技术决策和动态标准核对记录齐全 |
| 1 | 脚手架初始化 | `fs-scaffold` | `dev`/`build`/`lint`/`typecheck`/`test` 按仓库实际脚本通过 |
| 2 | 前端设计与开发 | `webapp-building` + `fs-frontend` + `fs-frontend-ui` | 先完成结构/视觉/状态/响应式/交互设计，再实现；页面可运行并通过可访问性与交互检查 |
| 3 | 后端开发 | `fs-backend` | API 契约、输入校验、统一错误格式、授权和前端消费路径就绪 |
| 4 | 数据库 | `fs-database` | 迁移可回滚、索引设计经确认 |
| 5 | 测试 | `fs-testing` | 前端组件、API/数据集成和关键 E2E 路径按风险覆盖 |
| 6 | 安全审查 | `fs-security` | 当前官方安全清单逐项核对，无未处置高危 |
| 7 | 性能优化 | `fs-performance` | 以实测基线和项目预算验证前端与后端性能 |
| 8 | 部署与文档 | `fs-deploy` + `fs-docs` | 生产可访问、README/API 文档完整 |

## 调度规则

1. **判断起点**: 用户说"新项目"→从阶段 0 开始; 说"加功能"→判断涉及范围, 从对应阶段切入; 说"修 bug"→先定位, 只进入相关阶段。
2. **每个阶段开始时**: 加载对应子技能, 完全按其规范执行。
3. **阶段衔接**: 记录完成内容、关键决策和验证证据；没有阻塞时直接进入下一阶段，最终统一交付。用户提出修改时回到相关阶段迭代。
4. **跨阶段影响**: 若阶段 3+ 发现需求变化, 回到 `fs-plan` 更新文档再继续, 保持文档与代码一致。
5. **标准合规**: 已有项目优先服从仓库、锁文件和兼容矩阵；新建项目、升级依赖或标准会影响实现时，执行现场核对对应官方文档、发布支持表和安全公告，并记录核对日期与依据，不凭记忆写版本号。
6. **前后端闭环**: 前端状态、表单和错误态必须映射到 API 契约；API 必须有真实的前端消费验证；数据迁移、测试、安全、性能和部署门禁都要覆盖这条用户路径。

## 默认技术方向(无特殊要求时)

优先选择与目标仓库兼容、维护活跃且有官方支持的主流方案。常见组合可以是 React/Next.js 或仓库已有前端、TypeScript、Route Handlers/Fastify/NestJS/FastAPI、关系型数据库与 Prisma/Drizzle、Vitest/Testing Library/Playwright 等，但每次项目都必须依据当前官方资料、锁文件和实际约束确认，不把框架名称或版本当成永久默认。

前端任务先加载 `webapp-building`，产出页面结构、视觉令牌、组件状态、响应式规则、键盘/指针交互和视觉验收点；只有新项目或用户明确要求脚手架时才使用其模板初始化脚本。
