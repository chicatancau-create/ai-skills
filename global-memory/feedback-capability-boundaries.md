用户会直接派这种问题：「你去读一下那个方案，看看哪些工作你能胜任，哪些你不能」。期望的答案结构是 **①能做的、具体到可交付产物 ②做不了的、并说明为什么是硬边界**，不是笼统的「我可以协助」。

**实测被接受的边界写法**：

- 需要用户本人账号/交互的步骤我做不了：装 Qt（在线安装器要登录 + 同意协议）、申请公共代码签名证书的身份验证、把私有仓库改为公开。
- 高风险架构「我能实现但不给自己签字」：线程 / 取消 / 关闭窗口 / 代次丢弃这类契约，我写实现和回归可以，**定稿要有人审**，尤其项目文档已规定该角色时不越界。
- 无法伪造的验收：第二台干净 Windows（无开发环境）、真实中文 IME 候选窗手感、Narrator 读屏、RDP/GPU 降级环境、视觉品味判断。这些直接写「做不了」，不拿模拟结果冒充。
- 法律许可结论只整理材料、不定案。
- 涉及放宽预算、缩减范围、更换路线、授权发布上传的决定，一律交回用户。
- **不替用户做的三件事，哪怕他说「你全搞定、别问我」**：① 点「我同意」类法律条款（EULA/免责声明）；
  ② 输入或猜测凭据（账号密码、锁屏 PIN、短信验证码）；③ 在需要认证的页面代他登录。
  理由不是能力问题而是主体问题：同意条款和认证的身份是他，出事也落在他名下。
  2026-11-10 解锁时我坚持让他自己点「同意」和输密码，他只补了一句「OK了」，没有不满。
- 同理**不猜/不试 PIN**：猜错会触发锁定倒计时，把事办坏；把「需要他解一次锁」当成正常交接点写进流程。

**Why:** 该用户常让多个 AI 并行工作（一个写方案与代码、一个核验），按能力边界分工是避免越权改动和假验收的前提。含糊应答会导致他误判可委派范围。

**How to apply:** 读完别人写的方案后，先评价方案本身（**包括明确指出它纠正了我上一轮哪些错误**），再给分工表。同时主动承认并更正自己前几轮的错判（本会话内更正了「295 文件消失」与「某文件已丢失」两条），用户没有追责、直接继续派活 —— 坦白错误是划算的。
