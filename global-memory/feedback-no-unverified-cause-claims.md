讲「根因」之前，要么手里有证据，要么明说这是猜的。**不要**把推测包装成结论让用户去按它行动。

**Why**：2026-09-21 修 Gemini 桌面版界面语言，我在只验证过**一个**账号首选语言是中文的情况下，收尾时写了一句「你那几个账号本身是英文偏好，这才是根因」。用户直接顶回来：「不可能，我每个账号都挨个去变成了中文」。他手里有我看不到的操作记录 —— 他把 4 个账号全改过了，而应用仍然英文。真正的根因是**应用自己的会话档案**（`%APPDATA%\Gemini`，多账号共用一份 cookie 库）里存着英文状态，账号语言对这个应用根本无效。我那句猜测不仅错，还把用户往「再去改一遍账号设置」这条死路上引。

同一轮里我还差点被自己的日志误导：应用日志 `Loading Gemini shell: https://gemini.google.com/app` 看着像补丁没生效，实际是它的打印函数主动剥掉了查询串。⇒ **日志/读数的缺失不等于事实的缺失**，和 [[reference-computer-use-blocked]] 里「应用面板会在取不到值时按 0 画」是同一类坑。

- **断言「不存在/没有数据」和断言根因一样危险，而且更难被发现.** 2026-10-05 我在好几轮里反复讲「没有 Electron 与原生的同机对照实测，所以性能结论只能靠原理排序」—— 数据其实一直躺在 `应用端/evidence/window-performance.json`（可见窗口 5352ms vs 72–145ms、工作集 455MiB vs 27MiB）。我为了否定一件事翻了源码树、CMake、文档，唯独没打开项目自己的 `evidence/` 目录。规则：**说「没有 X」之前，先按 X 可能存放的约定位置（evidence/、logs/、报告目录）逐个查过**，并说明查过哪里。
- **自己的验证脚手架也会造出假证据，而且会诱导我推翻正确结论.** 同一天我用 `.bat` 传中文路径复现 `qmlimportscanner` 失败，得到的是 cmd OEM 代码页把参数转烂的假象；据此我宣布「我原来说重了」—— 脚手架修好后原结论又成立。凡是「复现失败/结论翻转」，先质疑测量链路本身（参数怎么传的、环境变量抓没抓到、退出码是不是被后面的命令吞了），再改结论。详见 [[reference-qt-qml-build-traps]]。

- **二手来源的「数字」不能当官方要求，但厂商官方页的通用文案也不能反过来推翻实测。** 2026-10-31 这件事我错了两轮：
  ① 先把社区《全品牌 BL 解锁现状表》里的「绑定后等 168 小时」当硬约束写进操作卡，用户反弹「等那么长时间我干嘛」；
  ② 我去查小米官方 `mi.com/service/support/BL-loc`，原文是**「绑定后需要等待 72 小时或 360 小时」**，
  于是我当众"纠正"成「168 这个档官方根本不存在」—— **这个纠正本身才是错的**。
  后来拿官方解锁工具对本机本账号真跑一次，返回原文「您的账号与设备的绑定时间太短，请 **168 个小时**后再试」。
  ⇒ 分层规则：**会改变用户行动计划的量化约束（等待期、限额、版本要求、兼容性），厂商官方页的通用文案只是其中一层，
  最终判据是"针对这台设备/这个账号的服务端实际返回值"** —— 能真跑一次就别引用文案。
  社区表 → 官方页 → 实机返回，三者不一致时**以最后一层为准**，并把前两层的差异记进文档而不是抹掉。
  同一条也见 [[feedback-version-currency]]、[[project-k30ultra-root-prep]]。
- **反过来也成立：不要把"我没查到"说成"不存在"。** 同一天我先断言 cezanne「不存在免解锁 root 路子」，
  随后查到 MTK BootROM 强解覆盖天玑1200 及以下（MT6889 在范围内）、mtkclient 里 `var1=0xA # confirmed` 且
  `mt6885_payload.bin` 真实存在，于是当众收回。**说"不存在"之前必须说清查过哪些层**（工具源码、芯片表、payload 文件），
  否则和编造结论一样是过度断言。
- **推荐第三方工具/库之前，先看仓库是不是 archived、最后一次 release 是什么时候。** 同一次里我推荐了 `zygisk-Tweaker` 做机型伪装，随后查到它 **archived、2024-01 停更**；`Shamiko` 仓库直接 404 消失；`Scene` 的 GitHub release 停在 2021。三个都得临时换成现役替代（COPG / Zygisk Next / 酷安渠道）。⇒ 报工具名时顺手 `GET /repos/<r>` 看 `archived` + `pushed_at` + `releases/latest`，一次调用就能避免一个错推荐。
- **同一 URL 换镜像、换连接数都不动速率时，问题在自己这侧。** 2026-10-31 我连着给了三个错根因（镜像被限→worker 派错镜像→长连接被降速），真因是 Python urllib 的 TLS 握手被重置；直到拿同一段字节做 curl vs urllib 的 A/B 才暴露。四个来源报出**完全相同**的速率是测量被超时截断的信号。详见 [[reference-large-file-download-on-this-box]]。
- **2026-11-04 又是同两类的复发，值得单独记住"我没查就断言"的三种具体形态**：
  ① 我写「App 目录里没有 alpha 内核副本」——实际 `D:\Clash Verge\verge-mihomo-alpha.exe` 一直在，
  我**只翻了 `config\` 和 AppData 两个子路径就下了全称否定**。
  ⇒ 否定断言要按 **文件名 + 尺寸 + mtime 具名搜盘**（含回收站）之后再讲，并说清搜过哪些根。
  ② 我用 `READ_HINTS=('list','get','findone')` 这种**URL 子串启发式当判据**去分类端点读写，
  `register` 含 `get` ⇒ 一个 `POST {}` 真写进用户的 MySQL。
  ⇒ 判读写只能看**声明（方法 + 必填参数形状）**，不能看命名习惯。见 [[feedback-probing-side-effects-on-user-data]]。
  ③ 我据截图说「第三个 tab 没渲染」——是 `--window-size` 与 CSS 视口不一致把内容裁在画面外。
  ⇒ 见 [[reference-inapp-browser-verification]]。
- **2026-11-10 两次「状态断言」翻车，都发生在把"有记录"当成"在位/成立"**：
  ① 我据 `Get-PnpDevice` 里一条 `VID_0E8D&PID_0003  Status=Unknown` 就宣布「BROM 进去了」——
  同一份列表里明显没插的 `REDMI K90 Max` 也是 Unknown，说明 Unknown 只是残影。
  ② 我对「144 小时」给了两版根因（用户自己重绑过 / 设备长期离线不计时），用户一句「没点过」就把第一版推翻，
  第二版纯属猜测。真因是手机侧 toast「验证失败，请重新登录」= **账号会话失效导致绑定作废**。
  ⇒ 报「设备在不在」「绑定成没成」这类二值状态时，只认**当前进程能当场复现的证据**
  （`-PresentOnly`/`Status=OK`/实机返回值），不认库里的历史条目，也不把"数字不寻常"当根因。
  详见 [[reference-xiaomi-miui-root-automation]]。
- **我自己的脚手架/断言写法也会给出"假绿"**：`(Get-Acl).Access` 拼字符串拼出空串时 `-eq` 回 True、
  `Get-FileHash` 抛错只进我看不见的提权控制台（表现为日志缺行）。
  凡是"一致/通过"的断言，先看两侧原文是否真的取到了值。见 [[reference-unattended-elevated-scripts]]。

**How to apply**：
- 因果链里凡是**没被我自己测到**的那一环，说的时候带「我猜/待验证」，并给出一条能证伪它的命令或操作。
- **写进文档的归因也要能被单变量实验复核。** 我在翻译扩展的取证报告里把一次行为变化归给「CSS 的 `white-space` 复位改变了纵向占位」，方向和对象**都错了**：真正的原因是另一处修复（片段去重）撤掉了一个意外兜底。正确的做法不是再猜一次，而是设计**一次只改一个变量的实验**——在同一份 DOM 上只注入/撤销那一条样式，量 `scrollHeight` 前后差；再配上「四轮同一套用例并排」的对照表，归因立刻自证或自毁。凡是我只能讲机制、拿不出这种对照的，就应该写成「未查明」，别写成「说明 X 会导致 Y」。
- 顺带一条同源的收获：**「修复后某个计数变少了」不等于变好**。那次 grid-dark 的高度修复数从 2 掉到 0，读起来像"问题消失了"，实际是覆盖丢了——内容被 `overflow:hidden` 静默裁掉 55/35px。看到某项指标下降时先问"是不需要做了，还是没人做了"。
- **写给用户照敲的命令/菜单，我自己必须先跑过一遍。** 2026-10-09 连着犯了两次：
  ① 从 `agy.exe` 二进制里读到一句 `Please log out (/logout) and log back in (/login).`，就告诉用户
  「在会话里敲 `/login` 加账号」—— 终端实际回 `Unknown command: /login`（二进制里的字符串可能是别的
  产品/版本的文案，**字符串存在 ≠ 命令存在**）；② 让他跑 `D:\agy\ag.cmd`，漏了必需的 `-` 占位参数，
  壳子只打了一行 usage 就退出，他看到「这啥也没有啊」。两次都消耗了他明确说过很紧张的时间。
  规则：给步骤前先自己执行一次（能无头跑就跑，跑不了就用 computer-use 在真终端里走一遍），
  或者明确标注「这条我没验过，报错就把原文发我」。
- 用户的反证（「我每个账号都改过了」）优先级高于我的模型推断 —— 立刻收回原说法并改解释，不要找补。
- 用户已明确表达过零遗漏式审查要求（[[feedback-rigor-audit]]）：先复核**我自己**的断言，再报结论。
- 收尾别顺手加「另外大概是 X」这种没证据的补充说明，那是最容易出错的地方。
